# 브랜치 전략

## 개발 모델

트렁크 기반 개발 (Trunk-Based Development).

- 장기 브랜치: `main` 하나만 유지
- feature branch는 수명을 짧게 가져가고 PR을 통해 main에 머지
- release branch는 릴리스 시점에 main에서 분기 (필요 시)

브랜치는 단위 작업 단위로 따며 단위 작업의 진입, 진행, 종료 전체 흐름은 [unit-task-workflow.md](unit-task-workflow.md) 참조. 단위 작업의 정의는 [unit-task.md](unit-task.md) 참조. 트렁크 기반 개발에서는 보통 메인 머지 1회 = 브랜치 1개.

## 작업 공간

단위 작업은 그 작업 브랜치 전용 워크트리에서 한다. 저장소의 주 워크트리(main worktree; git이 저장소를 만들거나 클론할 때 생기는 첫 워크트리)는 `main`을 체크아웃한 채로 두고 다른 브랜치로 전환하지 않는다. 한 저장소를 여러 세션이나 작업자가 동시에 다룰 때 주 워크트리 하나를 같이 쓰면 한쪽의 브랜치 전환이 다른 쪽의 HEAD를 바꾸고, 커밋하지 않은 변경이 서로 섞인다. 워크트리를 나누면 작업마다 HEAD와 작업 파일이 따로 있어 이런 간섭이 생기지 않는다.

- 만들기: `git worktree add -b <브랜치> <경로> main`으로 브랜치와 워크트리를 함께 만든다. 이미 있는 브랜치로 돌아왔는데 워크트리가 없으면 `git worktree add <경로> <브랜치>`로 만든다. 워크트리 폴더 이름은 브랜치 이름의 `/`를 `-`로 바꿔 쓴다.
- 위치: 워크트리는 주 워크트리 바깥에 둔다. 주 워크트리 안에 두면 저장소를 훑는 도구(감사 스크립트, 검색, 테스트 수집, AI 도구의 지침 탐색)가 워크트리 사본까지 읽는다. 구체 경로는 인스턴스가 정한다.
- 따라오지 않는 것: git이 추적하지 않는 파일(로컬 설정, 가상 환경, 무시 목록에 든 산출물)은 새 워크트리에 없다. 작업에 필요하면 워크트리에서 다시 만든다. 서브모듈이 있는 저장소는 새 워크트리에서 `git submodule update --init`으로 서브모듈을 따로 받는다.
- 도구가 만드는 워크트리: 세션마다 워크트리를 만들어 주는 도구를 쓰면 그 워크트리와 위치를 따른다. 위치 규칙은 에이전트나 사람이 직접 만드는 워크트리에 적용한다.
- 예외: 파일을 바꾸지 않는 조회는 주 워크트리에서 해도 된다. 다른 프로그램이 정해진 경로의 주 워크트리를 직접 여는 저장소처럼 워크트리가 맞지 않는 저장소는 인스턴스가 예외로 정한다.
- 정리: 머지 뒤 `git worktree remove <경로>`로 워크트리를 지운 다음 `git branch -d <브랜치>`로 브랜치를 지운다. 워크트리에 체크아웃된 브랜치는 지워지지 않는다. 커밋하지 않은 변경이나 추적하지 않는 파일이 남은 워크트리와 서브모듈을 받은 워크트리는 `git worktree remove`가 거부한다. 이때는 워크트리에 남길 것이 없음을 확인한 뒤 `--force`를 붙인다 - `--force`는 커밋하지 않은 변경과 추적하지 않는 파일을 함께 지운다. 무시 목록에 든 파일은 `--force` 없이도 함께 지워진다. 머지 뒤 잔존 점검은 [unit-task-workflow/merge-types.md](unit-task-workflow/merge-types.md) "환경 안전망과 잔존 점검"을 따르고, 다른 세션이 만든 워크트리는 [session-boundaries.md](session-boundaries.md) "다른 세션 작업과의 격리"에 따라 건드리지 않는다.

## 브랜치 네이밍 룰

```
<type>/YYMMDD-<짧은-설명>
```

- 설명 부분은 영문 소문자, 케밥 케이스
- 날짜는 브랜치 생성일

### 예시

```
feature/260414-event-queue
fix/260414-retry-timeout
docs/260414-architecture-update
```

## 작업 브랜치 type

| type | 용도 |
|------|------|
| `feature` | 새로운 기능과 관련된 것 |
| `fix` | 오류와 같은 것을 수정했을 때 |
| `docs` | 문서와 관련하여 수정한 부분이 있을 때 |
| `style` | 코드의 변화와 관련없는 포맷이나 세미콜론 누락 등 |
| `refactor` | 코드의 리팩터링 |
| `test` | 테스트를 추가하거나 수정했을 때 |
| `chore` | build 관련, 패키지 매니저 설정 등 production code와 무관한 부분 |
